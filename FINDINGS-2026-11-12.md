# Findings — 2026-11-12 (passive build exists; injection blocked; ABI gap explained)

A passive monitor build was actually produced and audited since the first draft. This
records what is now known, with evidence.

## 1. A passive monitor `.ko` was built from source

- Build tree: `~/android/malachite-monitor-kernel/` (WSL). Driver target only (no Image).
- Candidate module vermagic: **6.1.167-android14-11** (`-maybe-dirty`), monitor enabled
  (strings show `enable sniffer mode` and `mtk_init_monitor_role`).
- It applied `patches/0001-gen4m-passive-monitor.patch` — `CONFIG_SNIFFER_RADIOTAP := y`
  plus a **monitor TX-drop guard** in `wlanHardStartXmit` (in radiotap mode the skb is
  freed and `NETDEV_TX_OK` returned). Capture only; it does **not** inject.
- Manifest (`manifest.lock.xml`): kernel `android_kernel_xiaomi_mt6878` @ `fc1616578…`
  on `revival/kmi-symbol-repair` (this is the 6.1.167 KMI-repair candidate from
  `device/xiaomi/malachite-kernel/SOURCE_MIGRATION.md`); vendor kernel_modules @ `ce0e095`.
- The saved `abi-baseline.log` is a **control** (stock vs stock, vermagic 6.1.115,
  388/388) — it did **not** check the 6.1.167 candidate.

## 2. ABI gap: 3 cfg80211 symbols — and why

The candidate (6.1.167) was checked against the **shipped 6.1.166 Image + modules** and
mismatched on three symbols, all exported by cfg80211:
`wiphy_new_nm`, `__cfg80211_alloc_event_skb`, `__cfg80211_alloc_reply_skb`
(candidate required CRCs `0xe15db472`, `0x39b9a226`, `0xbce3447e`).

Cause: the module is **6.1.167** but the test image's kernel/cfg80211 is **6.1.166**.
cfg80211's exported-symbol CRCs for those three changed across that sublevel (a struct/
signature delta in the cfg80211 headers). A module loads only if its imported CRCs equal
the running kernel's exported CRCs, so grafting the 6.1.167 module onto the 6.1.166 Image
fails on exactly those three. The other ~371 match because the GKI KMI is otherwise stable.

### Resolution (shortest route, reuse artifacts) — do NOT spend another CI build first
The three mismatches are the **residual of the KMI-symbol-repair effort** (166 vs 167).
Pick one, matched to the Image the test ROM will carry:

- **Option A (recommended, smallest):** build the gen4m module against the **exact kernel
  the shipped 6.1.166 Image was built from** (same `common` GKI + cfg80211 revision), not
  the `revival/kmi-symbol-repair` 6.1.167 branch. Then all cfg80211 CRCs match and it is a
  single-module `vendor_dlkm` swap. Change `manifest.lock.xml`'s `kernel-6.1` (and `common`)
  revisions to the shipped Image's before rebuilding.
- **Option B:** ship a complete, self-consistent 6.1.167 set (Image + all modules + the
  monitor driver) from one build. But this build produced **only the module**, so a full
  kernel+Image build is required — bigger.

Until the manifest's kernel revision matches the Image, another CI build reproduces the
same three mismatches. That is why the next build is on hold.

### Confirm before building (cannot run now — build SSD not mounted)
1. `tools/build_disk.sh up`.
2. Generate the shipped 6.1.166 Image's exported-symbol CRCs (image_exports JSON).
3. Run `~/android/malachite-monitor-kernel/verify-monitor-abi.py <candidate.ko>
   <prebuilt-dir> <image_exports.json>` to get the exact mismatch set against the real
   candidate (not the stock-vs-stock control).
4. Pin the kernel revision per Option A, then rebuild.

## 3. Injection (patch 0002) is blocked — keep it out
See `patches/blocked/README.md`. Two confirmed blockers at `ce0e095`:
(1) `ENUM_PKT_802_11_MGMT` is not in `enum ENUM_PKT_FLAG` (`gl_os.h` ~447–468), so enabling
`CFG_SUPPORT_TX_MGMT_USE_DATAQ` fails to compile; (2) monitor switch tears down the AIS STA
role (`gl_cfg80211.c` ~6789), so there is no BSS to transmit the injected frame on.

## 4. Firmware executable identification — separate plan
The three `soc7_0_ram_mcu_{1,1a,1b}_1_hdr.bin` blobs (`~/stock-208/fs_vendor/firmware/`)
are candidates; only headers/trailers were inspected, and MT6878 firmware is **preloaded by
the bootloader**, so it is not established which blob (if any) is the running Wi-Fi
executable. Plan, in order:
1. Tester captures **cold-boot + first Wi-Fi-enable** kernel logs. The gen4m `fw_dl` path
   (`chips/common/fw_dl.c`) logs the firmware **version string** and region/section layout
   and which file it pulls.
2. Correlate that version string + section offsets to the exact blob in the stock package.
3. Identify the connsys MCU **core/ISA and load address** from the blob header + the driver's
   fwdl region descriptors.
4. Only then: reconstruct one small function in C, compile, and **byte-compare**.
5. Treat **byte-matching and firmware authentication (signing) as separate questions** — a
   tester loads a trivially-altered blob to see if Wi-Fi still comes up (that answers whether
   a patched blob could ever load). Historical lead: the old XDA MediaTek combo-chip RE thread
   (MT6620/6628/6630 — different generation, use only as orientation).
