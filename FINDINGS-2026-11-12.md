- Manifest (`manifest.lock.xml`): kernel `android_kernel_xiaomi_mt6878` @ `fc1616578…`

## 2. ABI gap: 3 cfg80211 symbols — and why

The candidate (6.1.167) was checked against the **shipped 6.1.166 Image + modules** and
mismatched on three symbols, all exported by cfg80211:
`wiphy_new_nm`, `__cfg80211_alloc_event_skb`, `__cfg80211_alloc_reply_skb`
(candidate required CRCs `0xe15db472`, `0x39b9a226`, `0xbce3447e`).

### Confirmed on-device-tree 2026-11-12 (ABI check run)
Ran against the mounted prebuilts (`device/xiaomi/malachite-kernel`). The shipped
`cfg80211.ko` is actually **stock 6.1.115**; the candidate is **6.1.167**. Exact CRCs:

| symbol | stock cfg80211.ko provides | candidate requires |
| --- | --- | --- |
| `wiphy_new_nm` | `0x801af4b3` | `0xe15db472` |
| `__cfg80211_alloc_event_skb` | `0x8e689896` | `0x39b9a226` |
| `__cfg80211_alloc_reply_skb` | `0xe132fa57` | `0xbce3447e` |

Full verdict: candidate imports **374** symbols; compared against the stock driver
(which loads on the shipped Image, so its required CRCs == what the Image provides),
**exactly 3** differ — these three. All 363 other shared symbols match, so the core/GKI
KMI is fine. (Candidate also newly imports 8 `debugfs_*`/`simple_attr_*` core symbols from
the monitor build; those are standard GKI exports.) So the gap is purely **wlan ↔ the
stock 6.1.115 `cfg80211.ko`**, not a broad KMI break.

Cause: the module is **6.1.167** but the loaded `cfg80211.ko` is stock **6.1.115**.
cfg80211's exported-symbol CRCs for those three changed across that sublevel (a struct/
signature delta in the cfg80211 headers). A module loads only if its imported CRCs equal
the running kernel's exported CRCs, so grafting the 6.1.167 module onto the 6.1.166 Image
fails on exactly those three. The other ~371 match because the GKI KMI is otherwise stable.

### RESOLVED (2026-11-12): ship a 3-module matched swap — all already built
The same build tree already produced **cfg80211.ko and mac80211.ko at 6.1.167** next to the
wlan module. Shipping the three together as a matched set makes them internally consistent
and removes the gap. Verified with the mounted prebuilts:
- new `cfg80211.ko` (6.1.167) exports the 3 symbols at exactly the CRCs the wlan module needs,
  and its own 195 imports match the shipped Image exactly (0 diffs) — it loads on the 6.1.166 Image.
- new `mac80211.ko` (6.1.167): only 2 import diffs vs stock (`wiphy_new_nm`,
  `cfg80211_bss_color_notify`), both provided by the new cfg80211; all other imports match the Image.
- Only `mac80211` and the wlan driver consume cfg80211; only the wlan driver consumes mac80211 —
  all three are in the swap, so nothing else is affected.

So the passive monitor deliverable = replace **wlan_drv_gen4m_6878.ko + cfg80211.ko +
mac80211.ko** in `vendor_dlkm` with the three 6.1.167 modules from
`~/android/malachite-monitor-kernel/out/bazel/.../mgk_64_k61.user/` (net/wireless, net/mac80211,
and the gen4m build dir). No new kernel build needed. Deliver via a test ROM's `vendor_dlkm`
(robust) or a module that swaps all three; verify loaded `srcversion` on-device, then capture.

### (superseded) earlier resolution options — do NOT spend another CI build first
The three mismatches are the **residual of the KMI-symbol-repair effort** (166 vs 167).
Pick one, matched to the Image the test ROM will carry:

- **Option A (recommended, smallest):** make the wlan module's 3 cfg80211 imports match the
  **stock 6.1.115 `cfg80211.ko`** that actually ships in `vendor_dlkm`. Build the gen4m
  module against the stock cfg80211 KMI — feed the stock modules' `Module.symvers` (or build
  against the GKI/cfg80211 revision the stock 6.1.115 modules came from) so those CRCs stamp
  to `0x801af4b3 / 0x8e689896 / 0xe132fa57`, not the `revival/kmi-symbol-repair` 6.1.167
  values. Then it is a single-module `vendor_dlkm` swap. This is a KMI-alignment task in the
  kernel manifest, not a source change to the driver.
- **Option B:** ship a complete, self-consistent 6.1.167 set (Image + all modules + the
  monitor driver) from one build. But this build produced **only the module**, so a full
  kernel+Image build is required — bigger.

Until the manifest's kernel revision matches the Image, another CI build reproduces the
same three mismatches. That is why the next build is on hold.

## 3. Injection (patch 0002) is blocked — keep it out
See `patches/blocked/README.md`. Two confirmed blockers at `ce0e095`:
(1) `ENUM_PKT_802_11_MGMT` is not in `enum ENUM_PKT_FLAG` (`gl_os.h` ~447–468), so enabling
`CFG_SUPPORT_TX_MGMT_USE_DATAQ` fails to compile; (2) monitor switch tears down the AIS STA
role (`gl_cfg80211.c` ~6789), so there is no BSS to transmit the injected frame on.

## 4. Firmware executable identification — separate plan
The three `soc7_0_ram_mcu_{1,1a,1b}_1_hdr.bin` blobs (`~/stock-208/fs_vendor/firmware/`)
are candidates; only headers/trailers were inspected, and MT6878 firmware is **preloaded by
the bootloader**, so it is not established which blob (if any) is the running Wi-Fi
executable. Plan, in order:
1. Tester captures **cold-boot + first Wi-Fi-enable** kernel logs. The gen4m `fw_dl` path
   (`chips/common/fw_dl.c`) logs the firmware **version string** and region/section layout
   and which file it pulls.
2. Correlate that version string + section offsets to the exact blob in the stock package.
3. Identify the connsys MCU **core/ISA and load address** from the blob header + the driver's
   fwdl region descriptors.
4. Only then: reconstruct one small function in C, compile, and **byte-compare**.
5. Treat **byte-matching and firmware authentication (signing) as separate questions** — a
   tester loads a trivially-altered blob to see if Wi-Fi still comes up (that answers whether
   a patched blob could ever load). Historical lead: the old XDA MediaTek combo-chip RE thread
   (MT6620/6628/6630 — different generation, use only as orientation).
